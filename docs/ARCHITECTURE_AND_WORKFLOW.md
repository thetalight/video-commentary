# 项目整体逻辑与流程（当前实现）

核对日期：2026-09-24。本文依据当前仓库源码整理，不代表所有流程均已端到端验证通过。

本文区分三类内容：**当前实现**、**实现限制 / 已知风险**、**尚未落地的改进建议**。2026-09-22 更新：整片导演升级为 Story Pipeline v9，新增全片人物/关系模型和独立 Story Planner；整稿时长校验暂保留。

## 1. 项目定位与边界

这是一个 Tauri 桌面视频解说应用。用户提交视频链接后，应用下载原片、获得字幕，通过 AI 生成剪辑脚本，供用户审稿，最后配音并剪辑成片。

主流程：

```text
播放页链接
  → 下载原片
  → 平台字幕 → 视频内封文字字幕 → 本地画面硬字幕 OCR
  → 字幕质量检查与任务材料落盘
  → AI 导演：过滤 → 局部事实节拍 → 对白归属 → 全片 Story Model → Story Planner → Writer → Reviewer
  → 人工审稿 / 修改 / 重新生成
  → 按段配音 → 裁剪与画面时长对齐 → 拼接 → 可选烧录字幕
  → 原片 / 成片在桌面预览
```

关键边界：

- AI 导演的剧情依据是字幕时间戳与文本。片名、风格、原片时长等作为上下文，不向导演模型发送视频帧或音频。
- 原视频用于内封字幕检查、画面硬字幕 OCR、媒体信息读取和最终剪辑，不是导演阶段的多模态输入。
- 项目不使用 ASR，也不会从音轨猜写字幕。三种字幕来源均不可用时，任务停止并给出明确错误。
- 所有 AI 阶段固定使用本机 Ollama，不启用云模型、Cursor 或外部写稿兜底。下载与 Edge TTS 仍可能联网。
- “本地 Ollama”只代表导演请求走本机；下载和 edge-tts 配音仍可能联网。
- 自动跳过片头片尾和广告依赖字幕标记与模型判断，不是完整的视听广告检测系统。

## 3. 任务存储与配置

### 3.1 单一任务目录

新任务固定存放在源码根目录的 `inbox/{task_id}`。`jobs::repo_root()` 使用编译时 `CARGO_MANIFEST_DIR` 推导仓库根目录，因此当前打包结果仍与构建机器的源码位置有关，不是完全可搬迁的独立数据目录方案。

```text
inbox/
├── tasks.sqlite
└── {task_id}/
    ├── source.mp4                     原视频
    ├── META.json                      片名、链接、时长、风格等任务资料
    ├── job.json                       数据库任务状态的诊断快照
    ├── TRANSCRIPT.srt                 标准字幕；导演主要事实来源
    ├── TRANSCRIPT.normalized.json     结构化字幕材料
    ├── TRANSCRIPT.compact.txt         压缩 / 抽样字幕材料
    ├── SCHEMA.md                      导演 JSON 格式说明
    ├── STYLE.md                       风格与写作说明
    ├── director/runs/{revision}/
    │   ├── checkpoint.json
    │   ├── map/chunk-001.json          单块字幕的剧情节拍
    │   ├── beats.json                 合并后的剧情节拍
    │   ├── dialogue-attribution.json  关键台词的说话人、听话人、置信度与不确定性
    │   ├── story-model.json           全片人物、关系、线索与因果合同
    │   ├── story-plan.json            剧情取舍与 Narrative Unit 计划
    │   ├── chapters/                  分章草稿、事实裁决、核验稿
    │   └── final-plan.json
    ├── edit.json                      当前可执行导演脚本
    ├── commentary.md                  从脚本导出的可读解说稿
    ├── review/plan-{revision}.json     保存的脚本版本
    ├── tts/                           配音缓存
    ├── clips/                         剪辑缓存
    ├── renders/{edit_revision}/        成片版本留存
    ├── render-manifest.json            当前成片对应的脚本与设置版本
    ├── output.srt                     成片时间轴上的解说字幕
    └── output.mp4                     当前成片
```

目录按需产生，不是创建任务后所有文件立即齐全。下载器、内封字幕提取器和画面字幕 OCR 也可能留下来源字幕等辅助文件。

旧版 `<output>/jobs/{task_id}` 会迁入同名 inbox 任务。规范目录已有文件优先，旧版冲突文件放入 `legacy/`。设置里的输出目录目前被后端归一到仓库 inbox，并非任意路径都实际生效。

### 3.2 数据库与状态快照

SQLite 保存 `tasks`（任务）、`stage_runs`（阶段尝试）、`artifacts`（产物版本）、`events`（进度事件）。每个任务最多保留最近 2000 条进度事件；`job.json` 是便于诊断的派生快照。

启动时恢复上次中断的任务，并扫描已有任务资料。磁盘文件用于判断素材是否存在、脚本是否可读、成片是否对应当前版本；不能只根据一个页面状态判断任务是否完整。

### 3.3 应用配置与隐私

配置通过 Tauri Store 保存到应用数据目录的 `settings.json`，顶层键为 `config`。本机位置是 `/Users/esun/Library/Application Support/com.esun.video-commentary/settings.json`。

- AI 来源固定为本机 Ollama，只允许 `localhost / 127.0.0.1:11434`；设置中选择本机已安装模型。
- 最近一次已确认保存的本机 Ollama 模型为 `qwen3.8:27b-mlx`。这是本机配置记录，不是所有安装的默认值，也不证明模型已下载完整。
- 新版设置不保存云端 API Key；读取旧设置时会重写记录并移除旧云字段。
- 本地媒体访问范围在 `tauri.conf.json` 中限制为本机仓库 inbox；迁移路径时需要同步调整。

## 4. 下载与字幕获取

### 4.1 下载

`prepare_job` 校验任务 ID、读取配置并获得任务锁，再由 yt-dlp 下载到任务目录。站点识别、链接整理和一帆专用提取器在 `video_url.rs`、`ytdlp.rs` 与 `src-tauri/ytdlp_plugins/`。

一帆站点使用专用插件，并在未指定其他浏览器时默认尝试 Chrome Cookies。Cookies 和浏览器验证并不保证绕过站点 403；链接、登录状态、站点接口或提取器变化都可能导致失败。

### 4.2 字幕优先级

1. 先由 yt-dlp 获取平台可下载字幕，包括人工字幕和平台自动字幕候选。
2. 平台未提供独立字幕时，用 FFprobe 检查视频容器中的字幕轨，优先选择中文，其次日文、英文、韩文和未标语言的文字字幕轨，并提取为 SRT。
3. 仍没有字幕时，调用随应用打包的本地 macOS Vision OCR，抽取画面下方的硬字幕，合并连续重复字幕并剔除长期静止台标。
4. 将选中的来源字幕规范化为 `TRANSCRIPT.srt`，记录 `TRANSCRIPT.source.json`，再执行字幕质量检查。
5. 三种来源均不可用或质量明显不可靠时停止，不启用音轨语音识别兜底。

“视频画面上能看到字幕”不等于“平台提供可下载字幕文件”，因此硬字幕 OCR 是独立的最后一级。OCR 全程在本机运行，不上传视频帧。容器中的 PGS 等位图字幕目前不会被当作文字轨直接提取；若它并未烧进画面，当前版本会明确停止，而不是用 ASR 猜写。

### 4.3 质量检查与人工入口

质量检查关注提示词泄漏、异常语种字符、机械重复、低信息字幕行，是启发式检查，不是与原音逐句核对的准确率评测。少于 20 行时主要检查提示词泄漏，不能凭分数保证字幕正确。

任一来源字幕未通过检查时，应用保留字幕并暂停，不用其他来源静默覆盖。用户可查看原字幕，再选择：

- **重新获取最佳字幕**：复用原片，重新尝试平台字幕；失败后继续检查内封文字字幕和本地画面硬字幕 OCR。
- **重试 AI 导演**：复用已保存字幕，不重新下载或识别。

重新获取成功后会更新导演输入，因此不是普通导演重试的同义操作。

## 5. AI 导演：实际是多步骤 MAP / REDUCE 流程

### 5.1 过滤与剧情节拍（MAP）

先按字幕标记识别片头、片尾、广告等排除区间，并移除与这些区间重叠的字幕。如果启发式规则把全部字幕排空，会清除排除区间并退回原字幕，交给后续模型判断。

有效字幕按约 12000 的文本长度预算分块，逐块提取剧情节拍。每个节拍包含开始 / 结束时间、事件摘要、重要性、原声引用以及叙事层级等信息。提示词要求区分主线、采访 / 导语、片中节目、闪回和不确定层级，避免把片中节目内容当作主角经历。

分块结果逐一保存，合并、过滤并按原片顺序分配稳定 `B0001…` 编号，再由程序附加对应时间附近的只读原字幕证据，最后写入 `beats.json`。Story Builder 同时看到局部摘要和原字幕；冲突时提示以原字幕为准。这里处理的是传入的完整字幕条目，不是仅将 `TRANSCRIPT.compact.txt` 当作唯一导演输入。局部节拍是事实候选，不等于最终旁白段落。

节拍完成后增加独立的对白归属层。模型必须为每个节拍至少选择一条可逐字匹配的原字幕；凡会用于判断人物身份、关系、行动主体或因果的关键台词都要单独归属，每个节拍最多三条。系统结合相邻问答、直接称呼、第一/第二人称承接、人物出入场和连续状态，标注说话人、主要听话人、置信度及不确定性。低于 0.8 或存在冲突时，说话人强制降为“身份未确认”，不能获得人物命名权；未进入归属表的台词只作为场景上下文。结果写入 `dialogue-attribution.json`，不修改 `TRANSCRIPT.srt`。

### 5.2 全片 Story Model、Story Planner 与 Writer（REDUCE）

Story Builder 根据所有带编号节拍、原字幕证据和对白归属表生成 `story-model.json`，记录主角、欲望、冲突、代价、中心问题、因果链、人物弧线、`character_bible`、人物关系与故事线。人物事实和关系变化必须引用 `beat_id`；程序删除不存在的证据、重复人物 ID、无效关系和无证据事实。对白归属不确定时，Story Builder 只能保留中性人物或省略身份，不能把“被谈论的人”当成“正在说话的人”。

Story Planner 再根据 Story Model 和全部节拍生成 `story-plan.json`。Planner 明确省略低价值细节，并把同一戏剧目的下的多个局部事件合并成 Narrative Unit；每个 Unit 记录进入状态、转折、离开状态、旁白目标和原声策略。Unit 数量只有按片长计算的规划参考，不为数字拆段；如果输出退化成“一事件一 Unit”，程序会合并相邻低层单位，同时把遗漏的 importance 4–5 关键事件并入最近 Unit。

Writer 最后按 Narrative Unit 分章，每章最多约 4 个 Unit 或 14 个引用节拍。v11 的 Writer 只输出 `unit_id → narration` 的旁白脚本，不再同时猜时间码与镜头；程序依据该 Unit 的 `beat_ids` 生成 `EditSegment`。Story Planner 的交错 Unit 会先拆成时间单向的连续 run，避免一个大时间窗包住后续段落。每章输入包括全片人物合同、完整 Story Plan、当前 Units、对应节拍、字幕证据、上一章结尾和排除区间。详见 [Story Pipeline v11](./STORY_PIPELINE_V9.md)。

### 5.3 当前字数规则与旧版 361 / 368 报错

令 `S` 为过滤后非空字幕时间区间的并集长度，重叠字幕不重复计时，区间截断到原片时长范围。

```text
全稿最低字符数 = max(24, ceil(S × 1.2))
全稿建议最高字符数 = max(最低字符数, ceil(S × 1.8))
估算口播秒数 = narration 字符数之和 ÷ 4

分章依 Story Planner 的 Narrative Unit 决定，不再由字符目标或固定节拍数决定
章节不分配最低字数，没有逐章字数欠额
```

这里的 1.2 来自“有效字幕覆盖秒数 × 30% × 每秒 4 字”。**当前代码不是按原片总时长计算 30%，也不是按原字幕字数取 30%。** `AGENTS.md` 仍写原视频时长 30%，与当前实现存在口径差异，需要后续统一。

实际统计使用 Rust `chars().count()`，会计入标点、空格和非汉字字符，并非纯汉字数。建议最高字数主要用于提示，不是最终统一执行的硬上限。

当前每章流程：

```text
生成初稿 → 清理与时间轴规范化 → 保存安全候选 → 事实核验
  ├─ 合法裁决 → 修正或删除对应片段
  ├─ 裁决缺失/重复/证据无效 → 忽略该裁决并保留原段
  ├─ 核验服务或格式不可用 → 保存警告并保留安全候选
  └─ 有效裁决删除整章 → 根据字幕保守重写一次；仍为空则拒绝空章并恢复安全候选

全部章节合并 → 时间轴规范化 → 开场与整稿最低字符数校验
```

旧版曾把 368 设为章节硬门槛，361 即使只差 7 字，也会重写并失败。当前已删除该门槛，而不是仅添加 7 字容差：字幕依据与基础结构通过的短章节也能继续。

整集 12 轮累计补写和逐章“差几字就重写”均不在当前实现中。v11 在写作前计算一次 `narration-budget.json`：发布下限、带审核余量的 Writer 目标、证据上限与每个 Unit 的最低交付量都成为结构化输出合同。整稿“有效字幕覆盖时长 30%”仍是最终硬门槛，但正常流程不再等到终审后才发现短缺。

### 5.4 事实核验与选片约束

同一配置的本机 AI 来源执行事实核验，不是另一个独立模型交叉验证。每段裁决必须引用程序限定的本段字幕证据；缺失裁决、重复裁决或引用不匹配时，该条审稿意见无权改写原稿。不支持的断言可用带有效证据的修正文案替换，修正文案过短时可删除。

导演规范化还会：

- 清理解说套话，剔除过短文案和落入排除区间的片段。
- 对齐字幕时间，按原片时间排序，处理重叠；这意味着最终排列通常是原片时间顺序，不是任意倒叙蒙太奇。
- 普通选片上限按口播长度计算并约束到 4–20 秒范围，原声选片上限 12 秒；最终保留片段至少 0.8 秒。4 秒是常规规划尺度，不是所有片段都强制达到的下限。
- 模型给出的 `shots` 先裁剪到所属段落窗口，再按源时间排序、合并重叠并删除不足0.8秒的无效区间；段落为原声接力时清空多镜头并使用连续区间。归一化只收缩或合并模型已授权的画面，不向段外扩张。
- 首段强制解说主导，避免连续超过两段原声插入；原声保留还需节拍中有引用依据。
- 分章事实核验由程序给每段生成仅覆盖所选镜头的字幕证据编号；模型只能引用同段编号，避免自由复制字幕时跨段、漏字或混入相邻台词。
- 整片终审沿用同一证据编号原则，并进一步验证修复稿所选证据仍在新镜头范围内；全片摘要只用于判断重复，不能充当事实依据。
- 整片终审只运行一轮，只处理人物合同冲突、剧情顺序、称呼、实质重复和说话人元数据等整片级硬问题，不再反复进行文风压缩。每一项修改独立校验并原子应用；如果整轮修改会让旁白低于发布预算，则拒绝整轮并保留章节核验后的安全稿。
- 整片终审可能删除相邻段或改变口播长度，因此终审后必须再做一次确定性画面重排。重排仍无法覆盖预计口播的段落由本机模型在同段证据内压缩到程序给出的字符上限；模型输出无效时仅从原文尾部按完整分句删除，不补写新事实。写入最终稿前，阻断级画面缺口必须为零。
- 原声接力不是仅凭模型布尔值决定：预计口播结束后必须能从原字幕找到一个完整对白起点，并在本段保留至少4秒原声空间。发布前会安全扩展区间或取消接力；渲染获得真实配音时长后复核，失败则降级为纯解说而不是终止任务。
- 合并后检查开场禁用语与全稿最低字数，再写 `final-plan.json`、`edit.json`、`commentary.md`。

这些规则能降低幻觉风险，但不保证电影事实正确、覆盖所有关键因果或达到商业解说质量。

### 5.5 模型请求与输出失败

| 项目 | 本机 Ollama |
| --- | --- |
| 接口 | 回环地址 `/api/chat` |
| 地址限制 | localhost / 127.0.0.1，11434 端口 |
| 思考控制 | `think: false` |
| 结构约束 | `format` JSON Schema |
| 单次请求上限 | 3600 秒 |
| 连接超时 | 5 秒；模型列表请求 4 秒 |
| 网络代理 | 强制绕过代理 |

请求为非流式响应，因此生成期间页面主要展示阶段进度，不是 token 级实时进度。Ollama 上下文请求设为 65536；输出预算随阶段变化，局部节拍初始 4096、Story Model 与 Story Planner 初始 8192、章节初始 8192 token。

普通结构化 JSON 解析失败可再请求两次，增加输出预算，最高 32768。导演片段 JSON 另有一次完整重试及恢复已闭合片段的逻辑，恢复结果仍需后续校验。

`length` 表示输出 token 预算耗尽，不是网络超时；把等待上限改成 1 小时不能单独解决它。当前已识别“有 thinking、无 content”的响应并明确报错，不把思考内容当作导演脚本。

模型列表可用只代表 `/api/tags` 返回名称，不证明权重文件完整或 `/api/chat` 可生成。HTTP 403 额度问题、模型缺失、运行时模板不支持等，也不是靠 JSON 重试能解决的问题。

## 6. 审稿、重新生成与检查点

`edit.json` 是剪辑契约，核心结构为：

```json
{
  "title": "解说标题",
  "style": "剧情解说",
  "target_duration_secs": 3,
  "segments": [
    {
      "src_start": 10,
      "src_end": 16,
      "narration": "这里填写有字幕依据的解说。",
      "keep_original_audio": false
    }
  ]
}
```

示例仅展示字段。`target_duration_secs` 会由代码按文案长度重新估算，不是用户填写后强制兑现的渲染时长。

审稿台提供文案编辑、原字幕查看、原片 / 成片预览、解说文稿导出以及重新生成入口。保存时执行基础脚本校验，更新 `edit.json` 和 `commentary.md`，并存档到 `review/`。点击“导出解说文稿”会先保存页面上的当前改稿，再在任务的 `exports/` 中生成带段号、原片时间范围和完整旁白的 `解说文稿.txt`，并打开该目录；如果当前导演稿已有匹配的成片或粗剪配音时间轴，还会同时生成 `解说字幕.srt`。旧成片的字幕不会冒充当前改稿的字幕导出。人工保存和渲染入口使用基础校验，不会重新执行完整 AI 事实核验和逐章最低字数审查。基础校验最短片段为 0.4 秒，与 AI 规范化的 0.8 秒不完全一致。

检查点版本由字幕内容、标题 / 时长 / 跳过选项、来源、模型、风格和 `PROMPT_VERSION` 共同决定。当前提示词版本标记为 `director-v11-script-budget-linear-timeline`。切换模型、字幕或导演架构后会进入不同的检查点目录。旧检查点保留在磁盘但不作为新规则的已完成章节复用；字幕不需重新获取。

- **失败后重试**：复用相同版本的分块节拍、Story Model、Story Plan 和已核验章节；当前未完成章节不保证复用草稿。
- **成功稿不满意，重新生成**：已有脚本通过加载校验后，先存档，再清理导演检查点、当前脚本及成片清单，重新创作；原片和字幕不重做。
- 改变请求策略并不天然改变检查点版本。若希望旧结果全部失效，还需要明确更新版本或通过成功稿重新生成入口清理。

## 7. 配音与成片

1. 读取当前脚本后先进入统一的本地时间轴编译器。AI 新稿、恢复任务、人工审稿保存和重试成片均调用同一实现：原声对白前移出引导空间；无合法对白时改为纯解说；普通段吸收镜头间隙并在相邻段、排除区和片长边界内扩选；仍不足时按可用画面确定性删减文案；不足三秒且无法承载最短口播的碎片移除。编译结果再次通过硬校验后才进入配音。
2. 按片段顺序串行合成配音，优先 edge-tts；失败可退回 macOS `say`。这是配音兜底，不是导演写稿兜底。
3. 配音按“文案 + 音色”哈希缓存。复用前检查普通文件、非空且可读取有限正时长，坏 MP3 不会挡住可用 WAV；都不可用才重新配音。生成先写独立临时目录，经校验后重命名发布，失败不会留下新的正式空 MP3 缓存。剪辑缓存还加入实际音频内容哈希、原片版本、选片时间、原声音量、保留原声标记与尺寸，避免配音修复后误用旧剪辑。
4. 普通片段按实际配音长度消费已选画面，保持原速；不以定格或慢放补足口播。
5. 保留原声片段先播放引导，再从字幕确认的完整对白起点开放原声；实际 TTS 比预估更长导致交接失效时自动降级为纯解说。**当前仍生成 TTS，不是纯原声片段替代 TTS。**
6. 根据各成片段实际长度累加时间轴，写出 `output.srt`，拼接视频。
7. 开启字幕烧录时再执行烧录。当前烧录失败会保留未烧录的拼接视频作为 `output.mp4`，而不是必然判定整个渲染失败。
8. 写入 `render-manifest.json`，记录脚本和渲染设置版本，保存成片版本并更新状态。

当前预估时长、实际配音时长、最终成片时长是不同概念。原声和停顿会造成差异；渲染结束后没有重新按纯解说音频验证“原片 30%”。

统一编译层借鉴 NarratoAI 把解说 / 原声模式和“字数—画面时长”校验放在生成视频之前的思路，但保留本项目的原速播放、不定格、不慢放约束。

FFmpeg 选择逻辑已经改为检查能否启动，跳过依赖损坏的候选版本；ffprobe 独立选择可用候选，字幕烧录另检查 `subtitles` 滤镜。存在某个安装目录不等于依赖可运行。

## 8. 状态、失败重试与删除

| 页面状态 | 含义 |
| --- | --- |
| `queued` | 已入队，等待派发 |
| `running` | 某阶段执行中或等待后端资源 |
| `awaiting_director` | 素材已有，但字幕检查或导演生成尚未完成 |
| `ready` | 导演稿可审阅，尚未完成当前版本渲染 |
| `completed` | 成片已生成 |
| `failed` | 操作失败，保留阶段与错误信息 |

后端发出 `task-progress` 和 `task-complete` 事件，前端同时根据命令返回值更新状态。主要阶段包括 download、download_subtitle、transcribe、director、review、tts、render、burn。

重试按失败阶段与前端已知的资源可用性分支：

| 条件 | 处理 |
| --- | --- |
| 配音 / 渲染失败且已有稿 | 重新渲染，复用配音与剪辑缓存 |
| 拉取字幕失败且原片存在 | 重新拉取平台字幕 |
| 识别失败且原片存在 | 按当前识别设置重做字幕 |
| 导演失败且字幕存在 | 直接进入导演流程 |
| 只有原片 | 进入字幕识别 |
| 无素材但有链接 | 重新准备任务 / 下载 |
| 素材和链接都缺失 | 报错，不能自动恢复 |

“删除任务”是永久删除：确认后后端移除规范任务目录及已知旧版同名目录，删除数据库关联记录，再由前端移除列表项。运行中的任务前端不允许直接删除；后端同任务操作也有互斥锁。删除不经过废纸篓。

`clearFinished` 只从前端当前列表筛除完成 / 失败项，不调用磁盘删除接口；它和永久删除是不同语义，重新扫描时任务仍可能回来。

## 9. 已知限制与后续设计议题

以下是源码可见的行为或风险，不是本次已经修复的事项：

1. **整稿时长仍是硬门槛**：v11 已把门槛前置成 Unit 预算并为审核预留余量，但极端情况下（大量 Unit 被事实核验认定为完全无证据，或画面物理容量不足）仍会中止，而不会发布注水或声画不匹配的成片。
2. **需求与统计口径不一致**：原片 30%、有效字幕覆盖 30%、字符数 / 4、实际配音时长尚未统一；原声标记片段的文案也计入字符总数。
3. **事实核验不是事实保证**：字幕可有误，模型可能误判人物和叙事层级；同一模型自审及引用匹配不能证明整段推理完全正确。
4. **状态更新可能冲突**：部分导演失败路径先 `record_failure` 再 `emit_progress`；后者调用 `task_store::progress` 将任务写回 running，存在错误状态被覆盖的风险。
5. **渲染成功不等于字幕烧录成功**：烧录失败可以输出无烧录字幕成片，页面最终仍可显示成功。
6. **缓存验收仍有局限**：配音已增加非空与可读时长校验、临时文件发布；视频片段缓存额外要求 48kHz 双声道音轨，拼接前再次逐段验收，不合格缓存会自动删除重建。这仍不是逐帧完整解码验证。成片版本目录只以脚本版本分层，同一脚本不同设置的版本留存也有局限。
7. **恢复依赖多处状态**：前端内存、数据库和文件检查共同参与，重试时前端资源信息可能过时；不是单一严格状态机。
8. **本机路径耦合**：任务根目录和媒体访问白名单绑定源码路径；复制 app 到另一台机器并不自动完成数据迁移。
9. **可见进度不等于生成进度**：阶段百分比为人工映射，非流式 AI 请求可能长时间不更新；高百分比仍可能触发重写。

下一步可讨论“字数只作整稿提示、用人工标注集校准关键事件覆盖率、根据实际配音评估时长”的方案；其中取消章节字数门槛与重要节拍进入 Story Plan 已落地，其余不应描述为现有能力。

## 10. 独立开头样片路径（2026-09-09 新增，2026-09-10 更新）

更新：样片 LLM 调用已切换到锁定的 `rig-core 0.42.0`；原同模型一次 pass/fail 复核替换为逐段问题单与最多两轮局部修复。证据不足、评审遗漏、修复越界、无变化或问题增多即停止。候选 / 评审 / 修复记录在 `samples/reflection/run-{timestamp}`，页面可查看。一次创作最多 7 次模型调用，无嵌套格式重试；整片暂不使用此反思控制器或 Rig 客户端。详见 [V2 实施进度](/Users/product/video_commentary/docs/REFLECTION_SYSTEM_DESIGN.md)。

这是先验收整体风格的实验分支，不替换本文前述整片流程，也不对既有整片重新渲染。入口在审稿台 `OpeningSamplePanel`：

1. `generate_opening_sample` 读取原字幕（不读取原片画面作导演输入），应用现有跳过规则，派生清除说话人编号和孤立噪声的文本；从开头 20 分钟范围、约 24000 字以内构建 4–20 秒字幕候选窗口。这不是视觉镜头检测，时间窗口不保证等同于电影镜头。
2. 使用设置中的本机 Ollama：提炼矛盾与因果提纲 → 口语意群及多窗口选片 → 同模型另一次事实/重复信息复核。引文必须出现在所选窗口中，候选 ID、时序、重叠、画面储备由程序验证。模型复核仍可能漏检，不宣称消除幻觉；人工修改后的文案由用户核实，不自动冒充已复核。
3. 用户审阅、编辑文案或勾选同情节画面。`render_opening_sample` 校验草稿版本、字幕指纹、原片大小及修改时间，防止旧稿套到新素材。
4. 应用生成段落 TTS 并测量真实时长，将时长分配到选定窗口，每个窗口只裁短、以原速播放。任一段画面不够或短于 0.8 秒会停止并说明原因，绝不补冻帧。整体 60–90 秒仅为建议，偏离给提示，不凑字、不触发完整重写。
5. 新 `narration_montage` 仅映射解说音轨，做单遍响度归一，不混原片对白；配短句字幕（按字符比例估时）。如设置要求烧字幕而失败，会报错，不静默冒充成功。导出后再检查实际视频时长与配音差异。
6. 输出存入 `inbox/{task_id}/samples/run-{timestamp}/`，保留 `draft.json`、段落配音/剪辑、`sample.srt`、视频、`result.json`；`samples/latest.json` 为最近成功样片稿/成片索引。生成稿另存 `draft-{revision}.json`。失败试制的草稿在运行目录，前端也保留待修改内容；不覆盖之前成功视频。删除任务时随整个任务目录删除。

样片复用任务互斥锁与 AI/渲染并发槽，但使用独立 `sample-progress` 事件，不更改整片数据库状态。进度显示真实阶段文字，不假装流式生成百分比。当前未实现中途取消、样片阶段自动续跑或多版本 UI 切换；切换任务后可在文件夹找旧样片。样片不适用整片 30% 比例检查。

边界：尚未接入视觉理解、独立音效/BGM、原声桥段、情绪控制或逐字对齐，也未将多镜头样片模型迁移至整片。旧整片的变速/定格策略仍存在，不能把本分支的改进描述为所有成片已生效。

## 11. 渲染媒体合同与静音防线（2026-09-20）

整片仍按导演段落生成可复用剪辑，但缓存不再以“文件存在”作为可拼接的充分条件。所有普通解说、保留原声、环境声混音和背景音乐路径必须输出相同的媒体合同：视频 30fps / yuv420p，音频 AAC / 48kHz / 双声道。每个新剪辑写入临时文件后先验收音轨，合格才原子发布到缓存；命中旧缓存时同样验收，不合格即删除并重建；最终拼接前再对全部输入做一次硬校验。

这条防线来自一次真实故障：同一粗剪相邻片段的音轨分别是 44.1kHz 和 96kHz，源 TTS 文件均有有效响度，但 MP4 concat 在采样率边界生成了超过 16 秒的静音，且命令返回成功。仅在最终成片重编码音频不足以补救，因为错误已经发生在 concat 对输入包时间基的解释阶段。当前版本同时重建连续音频时间戳，并升级渲染与剪辑缓存指纹，确保旧规格素材不会继续复用。

质量检查仍保留为发布闸门：只阻止与解说字幕重叠的长静音；没有解说字幕覆盖的安静原声区间只记录，不误判为配音丢失。它负责发现新的未知问题，而不再承担修复已知采样率不一致的职责。

本次故障证据、开源项目对照和音频主时间轴演进方案见 [成片工作流深度检查](./RENDER_PIPELINE_REVIEW_2026-09-20.md)。

导演文风已经由短视频钩子模板升级为“中心问题、人物弧线、关系变化、结尾回应”的深度叙事结构。旧导演检查点不会复用；整片复核后增加本地 AI 人物称呼专项修订，并以程序硬校验阻止 ASR 说话人编号进入成片。设计与边界见 [深度电影解说改造](./COMMENTARY_STYLE_REDESIGN_2026-09-21.md)。
