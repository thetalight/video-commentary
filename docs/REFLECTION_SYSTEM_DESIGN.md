# 视频解说系统 V2：基于 Reflection 的全流程设计

日期：2026-09-10。状态：总体设计，已落地首个样片试点；其余规划不是当前功能说明。

### 实施进度（2026-09-10）

- 已锁定 `rig-core = 0.42.0`，样片的提纲、初稿、评审和修复通过 Rig 调用本机 Ollama；整片也固定为本机 Ollama，并加入分批全稿评审。
- 已增加 `llm.rs` 薄封装与 `reflection.rs`。样片初稿后逐段评审，最多两轮限定段号修复；遗漏评审、未知证据、旧版本修复、越界修改、无变化与问题数量增加均停止。
- 每次样片创作最多 7 次模型调用（提纲 + 初稿 + 3 次评审 + 2 次修复），没有内部自动格式重试。空正文、仅思考、长度截断不会成为成功稿。
- 草稿、较好候选、评审、修复与结果保存在 `samples/reflection/run-{timestamp}/`。界面可查看最近创作的逐段评审与打开记录；失败不覆盖旧样片或整片。
- 已用本机假服务器验证 Rig 发出的 Ollama `/api/chat` 参数与 schema；这不是对真实本机模型的端到端验收。
- 尚未完成 P0–P5 全部内容：未新增统一 SQLite 运行/依赖图，未实现全片 Reflection、多轨整片重构、token/费用预算、取消续跑、独立评审模型配置及实片 A/B。当前较好候选按待修改段数保留，尚非设计中的严重度排序。

下文标注的拟议能力仍作为后续验收清单，不能依据本进度将整个 V2 标为完成。

目标：让每一次修改都有具体问题、字幕依据、明确范围和验收结果；让系统从“任务跑完”转向“产物可检查、质量可改进”。不承诺一次生成必过或自动达到商业成片水平。

## 1. 设计结论与参考边界

保留 Tauri + React + Rust、SQLite、本机 Ollama 和应用调用的媒体工具。重构的是流程控制、数据模型与质量验收，不是换一个模型名称或在提示词末尾加“请反思”。

按用户补充要求，LLM 基础设施采用 [Rig](https://github.com/0xPlaygrounds/rig)，不重复实现通用模型客户端和 Agent 基础抽象。Rig 负责模型能力，Reflection 控制器负责本项目的质量规则与运行治理。

你提供的 [Reflection 章节](https://adp.xindoo.xyz/chapters/Chapter%204_%20Reflection/) 将生成、评审和改进组织为反馈循环，并区分生产者与评审者。本方案以此为出发点，加入项目所需的证据约束、版本管理和局部重算。以下具体模块、阈值和数据结构均为本项目设计，不是原文现成方案。

流程控制必须由程序掌握。Google [ADK 循环工作流文档](https://adk.dev/agents/workflow-agents/loop-agents/) 同样要求明确设置终止机制；本文借鉴有界循环思想，不引入 ADK、LangChain 或额外 Python 编排服务。

必须保持的边界：

- 导演只依据字幕文本和时间戳；片名不构成剧情证据，原视频不是导演模型输入。
- 保留原始字幕和 `META.json`；清洗、纠错建议、人工确认以派生版本保存，不修改原文。
- 不启用 Cursor 或外部写稿兜底；设置错误、模型不可用、证据缺失如实显示。
- 下载、识别、配音、FFmpeg 均由桌面应用负责，不由模型生成任意命令执行。
- 片段数不设上限；普通选片通常 4–20 秒，原声 4–12 秒，任何实际选片至少 0.8 秒。
- 所有任务资源、样片、评审和版本都在源码下 `inbox/{task_id}`。

## 2. 当前架构哪些保留、哪些重构

| 当前模块 | 当前局限 | V2 处理 |
| --- | --- | --- |
| 下载、字幕适配器、依赖检测 | 外部故障与内容质量问题容易混在一个错误入口 | 保留实现，统一类型化错误与恢复动作 |
| `director.rs` MAP / REDUCE | 有事实核验，但缺少可追踪问题单和通用局部修复循环 | 保留字幕分块、节拍提取，拆出创作、评审、修复职责 |
| `EditSegment` | 一条文案只配一个源区间，难以自然安排音画 | 引入段落、事实声明、多个镜头和独立音轨 |
| `sample.rs` | 已有多画面样片，复核失败直接结束；未统一进入任务状态 | 作为 V2 首个试点，接入统一运行记录与反思控制器 |
| `pipeline.rs` | 同时承担业务、调度、写文件、发布产物 | 缩减为命令入口，调度与发布下沉到独立模块 |
| `task_store.rs` | 当前 artifacts 主键为任务 + 类型，不能完整表达版本依赖 | 新增版本表和依赖关系，保留旧表兼容读取 |
| 前端任务队列 | 前端也判断重试路径，样片进度另成体系 | 后端成为运行状态唯一权威，前端展示快照与事件 |
| 整片渲染 | 仍存在变速、定格和原声与口播竞争 | 新路径使用原速多镜头、独立原声段、真实媒体验收 |

当前样片不等于整套 V2 已实现；本文不把旧稿导入后自动标记为“通过新评审”。

## 3. 总体流程

```text
任务与制作要求
  → 下载 / 字幕获取 / 工具预检
  → 字幕证据库（质量评审，必要时等待补充材料）
  → MAP：剧情节拍与叙事层级
  → REDUCE：整片因果蓝图
  → 分段解说稿 ←→ 事实与叙事评审 ←→ 定点修复
  → 开头样片：配音 → 多镜头时间线 → 渲染 → 人工确认风格
  → 全片扩展与审稿
  → 段落配音 ←→ 声音验收
  → 剪辑时间线 ←→ 音画时长与连续性验收
  → 候选成片 ←→ 文件 / 字幕 / 音轨验收
  → 人工确认 → 发布成片
```

每个双向反馈只回到问题所属模块，不默认重跑整条链路。样片使用全片蓝图选择开头，而不是仅理解原片前 20 分钟后假定整片主题。样片确认只冻结风格偏好，不代表后续剧情事实已经合格。

## 4. Reflection 的执行单元

### 4.1 四个逻辑职责

这些是应用内职责，可以由同一模型的隔离调用承担，不需要启动四个常驻服务。

1. **创作者**：根据已确认证据、制作要求生成候选版本，不能批准自己的版本。
2. **评审者**：检查固定版本，输出具体问题及依据，不能直接修改稿件或操作文件。
3. **修复者**：根据问题单提交限定范围的替换内容，不能悄悄重写通过的章节。
4. **控制器（Rust）**：校验、应用修改、复核、判断退步、控制预算、发布或转人工。

写作与评审使用不同系统提示和独立上下文。评审输入为制作要求、待审产物、相关原字幕及必要的前后文，不把创作者的自我辩护作为事实。保留简短判定依据，不收集或依赖模型私有思考过程。

可在设置中分别选择创作模型与评审模型；默认复用当前来源但隔离调用，不宣称两次同模型调用等同于独立事实验证。跨模型评审是可选项，不是消除幻觉的保证。

### 4.2 评审有三种结果

- `pass`：本次检查范围通过；必须说明检查覆盖范围与版本。
- `revise`：有可执行的修改意见及必要证据。
- `insufficient_evidence`：证据不足，不能靠模型重新编写获得事实，应回到素材阶段或等待人工。

规则检查与模型意见分开记录。引用存在不等于整句叙述成立；必须逐项核对人物、动作、地点、因果和叙事层级。

### 4.3 问题单契约

示例仅说明结构，ID 和引文位置需由真实任务填充：

```json
{
  "review_id": "review-007",
  "artifact_revision": "script-v3",
  "rubric_version": "narration-v2",
  "verdict": "revise",
  "coverage": {"reviewed": ["p-012"], "unreviewed": []},
  "issues": [{
    "id": "issue-021",
    "severity": "blocker",
    "category": "unsupported_claim",
    "target_id": "claim-034",
    "evidence_ids": ["sub-0087", "sub-0088"],
    "reason": "所引对白不能证明该动作发生在主角身上",
    "repair_action": "rewrite_claim",
    "allowed_targets": ["p-012"],
    "acceptance": "删除无依据归属，保留字幕能够证明的事件"
  }]
}
```

每项问题必须有分类、目标、依据或明确缺证说明、修改动作和复核标准。“不够高级”“再饱满一点”只能成为用户偏好线索，不能直接启动无限重写。

程序检查评审覆盖了所有目标；缺失段落不是默认通过。修复请求带 `base_revision`、`issue_ids`、`replace_blocks`、`expected_unchanged_hashes`，只支持预定义替换动作，不执行任意路径或脚本。版本已变化则拒绝旧修复。

### 4.4 有界循环与保留较好版本

建议初始策略（待 A/B 调整）：

- 每个蓝图或段落：初稿 + 最多 2 次局部修复；同一稳定问题 ID 的额度不因上游回退重置。
- 一次修复未解决目标问题且出现内容重复 / 新阻断问题，回退该候选；连续两次无改善则停止。
- 先比较规则阻断项和事实问题，再比较关键因果覆盖，最后考虑风格；不靠平均分掩盖事实错误。
- “最佳版本”可以仍有待处理问题，必须标为待审，不能因为预算耗尽而宣布成功。
- 大纲确需重建时作为新的显式运行分支，不静默在局部修复里重写全片。
- API 传输重试与内容修复分别计数，所有请求同时计入任务总调用和 token 预算，防止嵌套循环放大。
- 全片按工作单元分批运行；任务记录累计调用、token、耗时和付费费用（价格未配置则显示未知）。达到用户预算则暂停，用户主动继续才追加预算。
- Ollama 单次请求可保留现有 1 小时上限，但这不是整个运行的成本或时长上限；停止任务应能取消等待和应用持有的子进程，不保证远端立即停止计费。

停止后给出具体选择：查看最佳稿、补充证据、手改问题段、换模型或追加预算。禁止自动降低事实标准、恢复已排除广告，或用无关剧情凑字。

## 5. 分阶段的产物、评审和修复

| 阶段 | 产物 | 检查者与检查内容 | 失败去向 |
| --- | --- | --- | --- |
| 下载与预检 | 媒体清单、依赖状态 | 程序检查可访问性、文件可解码、音视频轨道 | 403 / 认证交给用户处理；不让模型反复重试绕过 |
| 字幕 | 不可变字幕版本、质量报告 | 程序查时间戳、重复、语种异常；模型标记不确定语义，不擅自纠正事实 | 重新拉取、用户导入或经授权识别缺失部分 |
| MAP 节拍 | 事件、证据 ID、叙事层级 | 原句是否支持事件，采访 / 回忆 / 剧中剧是否被错误归属 | 修正对应事件；缺证转人工 |
| REDUCE 蓝图 | 主线、因果边、开头与兑现、关键事件清单 | 因果能否追溯到字幕、关键转折是否遗漏、顺序是否自相矛盾 | 修改蓝图节点并失效其下游段落 |
| 文案 | 段落、事实声明、节拍引用 | 事实审查 + 叙事审查，检查重复、流水账、钩子兑现与口语性 | 只重写相关意群，必要时请求补充相关字幕 |
| 配音 | 段落音频、实际时长、所用声音配置 | 程序查非空、完整解码、静音、削波；人试听发音与情绪 | 重合成该段；换声线则重新确认声音样片 |
| 剪辑 | 原速多镜头时间线、独立音轨 | 程序查区间、覆盖、排除段、音轨冲突；文本评审查候选字幕与段落关联 | 补选同情节窗口、缩短冗余文案或调整原声段 |
| 成片 | 候选视频、字幕、验收报告 | 应用完整解码检查、轨道和时长对齐；用户观看内容效果 | 只返工异常段或封装阶段 |

没有音频理解或视觉能力时，相关主观质量显示“未自动验证”，不能让只读文本的评审者声称听过配音、看过画面。字幕窗口并非视觉镜头，音画匹配最终仍需人工观看。

## 6. 数据模型：从单片段改成故事段落与多轨时间线

V2 使用独立 `schema_version = 2`，不要往旧 `EditSegment` 塞更多隐式含义。

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| `EvidenceEntry` | 原字幕版本、稳定 ID、时间、原文、派生文本、质量标记 | 原文不可变；每条修正记录来源与人工确认 |
| `StoryBeat` | ID、事实声明、字幕 ID、层级、相关人物、未知项 | 层级可为主线 / 闪回 / 剧中剧 / 采访 / 未知，不能把未知强行归主线 |
| `StoryBlueprint` | 节拍顺序、因果边、关键事件、钩子、兑现 | 关键事件清单在写稿前确定，不能由文案自报覆盖率 |
| `NarrationBlock` | 稳定 ID、口播文本、claims、beat_ids、语气与停顿提示 | 一个完整意群；字数不是内容单位 |
| `Claim` | 声明文本、支持 / 矛盾证据、判定 | 单一引文不能为整段多项断言背书 |
| `VisualSelection` | block_id、多个源区间、关联字幕 ID、使用目的 | 不跨排除区间；记录实际使用区间而非只记候选 |
| `AudioBlock` | narration / original / ambience / music、文件版本、时间线位置、增益 | 原声对白独立于口播；音乐使用合法用户素材且可关闭 |
| `Timeline` | 实际输出时间、shot_ids、audio_ids、caption_ids | 由实测音频驱动，不靠总字符数拉伸画面 |
| `ReviewReport` | 目标版本、检查器版本、覆盖范围、问题单、结论 | 报告只能证明对应版本和已执行检查 |

文案与镜头分别存储，允许一个段落搭配多个画面；一个原声段可以没有解说，解决当前旧结构要求每段都有 narration 的限制。

镜头选取不能只把每个候选从头按比例裁短：可能裁掉关键证据所在时间。V2 为选片标出必须保留的字幕时间区间，在满足该区间后分配剩余画面；不足时补选或修文案，不延伸到未知场景。字幕只证明文本关联，不证明画面中每个视觉动作。

## 7. 文案和时长的验收口径

### 7.1 先冻结口径，不能偷偷混用

当前存在规范冲突：`AGENTS.md` 要求原片时长的 30%，实现却按有效字幕覆盖时长计算。本次仅设计，不改运行行为，也不修改规范。

V2 默认按现行项目规范设计：整片纯口播至少原片时长的 30%。创建制作要求时显式显示分母、目标和规则版本，并保存到运行配置。若用户希望改成“有效字幕时长”或软建议，应先明确确认并统一规范、前后端与测试，再对新运行生效，不能由模型自行选择较容易的口径。

- 写稿时每秒约 4 个汉字只作预算估算；不为每章分配字数欠额。
- 最终校验用已生成解说音轨中的有效口播时长；独立原声、背景音乐和人为填充静音不计入。自然短停顿的统计规则需固定版本；有效发声可用应用内 VAD 辅助估计并记录误差。
- 字符数、估计口播、实测口播、原声时长、最终成片时长在 UI 分开显示。
- 样片是试制，不适用整片 30%；60–90 秒为建议，偏离只提示。
- 素材证据无法支撑要求时显示“目标与可证实内容冲突”。保留可用稿，请用户调整要求或补充字幕；不生成广告、重复剧情、慢速配音或静音充数。

### 7.2 不再用字数代替“饱满”

叙事评审检查：关键事件是否完整、动机—选择—后果是否衔接、解释是否有证据、是否多段重复同一信息、开头提出的问题是否兑现。饱满可以意味着增加遗漏的有证据事件，也可以意味着删除重复句后把因果讲清楚。

程序硬门槛包括结构可解析、时间合法、引用真实、无未解决阻断事实问题；风格评分只辅助排序，初期不设“80 分自动商业合格”等未经验证的门槛。对于评审者意见冲突或事实不确定，转人工，不简单多数投票。

## 8. 配音、剪辑和成片质量闭环

- 先提供声音试听与开头样片，再生成全片；按意群生成音频，保留合理停顿。
- 使用实际供应商支持的语速、语气参数；不支持时明确显示，不能只存一个情绪标签就声称实现情绪配音。
- 单段声音失败不默默切换成另一种声音混入全片；可提示重试或确认切换，若切换则对受影响音轨统一重做。
- 普通口播段默认关闭原片对白；原声亮点在独立区间播放，前后用文案承接，不同时争抢主声。
- 背景音乐是可选独立层，只有具备来源明确的音乐素材才启用；不把加音乐当作修复剧情错误的手段。
- 不使用定格、循环播放或大幅变速解决解说过长；不足的段落返回选片或文案修复。
- 字幕采用短句、合理换行和安全区。逐字对齐能力未接入前，比例估时必须标为估时；后续可用对生成配音的对齐服务提升同步，不重新识别原片替代导演字幕。
- 成片检查至少包括完整解码、音视频轨道、实测时长、字幕边界与烧录结果。黑场 / 静帧检测只标记可疑时间段，合法电影静镜不能自动判错。
- 输出先为候选版本，通过技术验收后可预览；质量确认前不能标成“用户已满意”。

## 9. 状态、版本和断点恢复

### 9.1 后端状态为准

任务与运行分开：一个任务可有多次 sample / full / repair 运行。建议运行状态为 `queued / running / awaiting_input / ready_for_review / failed / canceled / completed`，阶段另记，避免把“AI 稿待修改”和“HTTP 403”都叫导演失败。

命令返回 `run_id` 后异步执行。事件带 `task_id`、`run_id`、递增序号和阶段；页面重连先读取快照，再补事件。百分比未知时展示阶段、已完成工作单元、耗时，而不是长期固定 30%。

运行租约或心跳用于识别进程中断；恢复只续接已发布且依赖版本匹配的产物。用户点击重试失败单元不重拉字幕；点击重新创作则创建新版本分支。

### 9.2 局部失效规则

| 变化 | 需要重做 | 可复用 |
| --- | --- | --- |
| 一段口播措辞 | 该段事实复核、TTS、相关时间线、最终拼接验收 | 原片、字幕、未改段音频 / 视频 |
| 一段选片 | 该段选片检查、渲染和受影响字幕时间线 | 文案及配音 |
| 声音配置 | 相应音频、时长适配、输出时间线和渲染 | 字幕、通过的故事稿 |
| 字幕版本 | 依赖这些字幕的节拍、蓝图 / 段落评审及下游 | 原片与不受影响、依赖可证明一致的产物 |
| 蓝图关键因果 | 关联章节及全局连续性评审 | 与变动无关的已确认素材 |
| 评审规则 / 模型 | 相关评审报告 | 候选稿可先重审，不立即重写 |

所有产物记录内容哈希、输入版本、模型 / 提示版本、工具 / 声音配置版本。文件存在不代表缓存有效。旧事件不能覆盖新运行状态。

### 9.3 文件与数据库

```text
inbox/{task_id}/
  source.mp4 / META.json / TRANSCRIPT.srt   保留现有资源
  evidence/{revision}/                    派生字幕与质量报告
  runs/{run_id}/
    manifest.json                         输入版本、预算、模式、状态
    story/                                节拍、蓝图、覆盖检查
    script/{revision}.json                 段落、声明、选片
    reviews/{review_id}.json               结构化问题单
    repairs/{repair_id}.json               定点修改与验收结果
    audio/ / timeline/ / renders/          运行产物
    acceptance.json                       技术与人工验收记录
  published.json                          当前发布版本指针
```

SQLite 建议新增 `runs`、`artifact_versions`、`artifact_dependencies`、`reviews`、`repair_attempts`、`approvals`；与现有 `tasks` 关联。文件写临时路径，校验后原子发布，再提交数据库索引与事务事件；启动时对未完成发布作一致性恢复。`published.json` 是数据库发布记录的派生索引，可重建，不形成第二个权威状态。

保留所有候选不意味着自动复制大视频；素材只引用，缓存按内容复用。任意旧文件路径都要规范化校验在任务目录内，避免符号链接越界。

### 9.4 真删除与取消

删除先显示影响范围并确认，后台标记 deleting、停止新调度、取消运行并等待写入者退出，再彻底删除该任务目录与数据库关联资源。前端只在确认成功后移除任务；失败显示具体残留项，不能假装删除。

删除中的任务禁止扫描器重新导入；需要持久化删除标记处理崩溃恢复。日志不留字幕全文或媒体副本到任务目录之外。用户级风格记忆只保存明确同意的抽象偏好，不保留被删除任务的剧情材料。

## 10. 模型接入、错误分类和安全

### 10.1 Rig 的复用边界

检索日期：2026-09-10。官方仓库提供统一模型接口与 Agent / 结构化提取能力；仓库同时提示版本可能有破坏性变化。因此先选定已发布、可编译的版本并锁定依赖，不直接追踪 `main`。当前主分支与历史教程的 crate 划分可能不同，不在设计阶段抄一个未经编译验证的 Cargo 配置。参见 [Rig 官方仓库](https://github.com/0xPlaygrounds/rig)。

| 能力 | 处理方式 |
| --- | --- |
| 模型请求、消息结构、Agent 构建 | 复用选定版本 Rig 的 provider / agent API |
| 类型化结构提取 | 优先复用 Rig 的类型化提取；项目仍执行业务 schema、引用与事实校验 |
| 创作者、评审者、修复者 | 基于 Rig 构建隔离角色，固定输入类型、系统提示与输出类型 |
| 流式事件 / 调用观测 | 优先复用 Rig 支持的流式和 hook 能力，映射到应用进度；未提供指标显示未知 |
| 提示版本、字幕证据、质量问题单 | 项目自己的领域逻辑，不放进通用 SDK |
| 有界反思、修复范围、预算、较好版本回退 | 项目控制器管理，不能等同于 Agent 自动多轮工具调用 |
| SQLite、任务锁、恢复、删除、媒体发布 | 保留项目实现；Rig 的模型运行状态不能替代桌面任务持久化 |
| 测试 | 使用可替换的窄接口 + 固定响应 / HTTP 合约测试，不为测试另造通用 Agent 框架 |

建议调用层次：`pipeline → reflection / director → llm（薄封装）→ Rig → 本机 Ollama`。薄封装只处理设置、安全回环地址、应用错误分类和度量，不再维护一套平行的消息协议、模型注册系统或复杂路由 DSL。

### 10.2 本机 Ollama 接入方案

优先使用 Rig 原生 Ollama provider，其存在可在 [官方 crate 文档](https://docs.rs/rig-core/latest/rig_core/providers/ollama/index.html) 核对。模型名沿用用户设置；验证选定版本对 `think:false`、JSON schema、上下文 / 输出 token 参数、结束原因和 1 小时超时的具体支持，不擅自换成本地兼容接口而丢失这些行为。

需要用选定 Rig 版本通过的接入合约：

1. 所有模型请求只允许回环地址并强制不走代理；设置结构不保存云端密钥。
2. 正常结构化响应能解码成段落 / 评审类型；空正文、仅 thinking、`length` 截断和错误字段类型不得变成成功。
3. 保留本机服务 429、500、超时、连接拒绝等错误的可操作提示，不只显示通用 SDK 错误。
4. 能设置并验证所需 provider 参数；区分供应商原生 schema 约束和通过工具调用实现的提取，不能默认两者等价。
5. token 用量和结束原因能取得则保留，缺失则为未知；流式最终结果仍需完整校验后才能发布。
6. SDK 内部自动重试 / Agent 多轮上限与外层预算统一；禁止三层各自重试造成调用次数相乘。
7. 实测取消、长等待、错误响应与本机 Rust / Tauri 编译兼容性，不把文档支持当成本机验证通过。

若选定版本缺少单个必须参数，优先使用其扩展参数或可注入传输能力；仍不足则提出最小适配 / 上游修复，记录原因与移除条件，不复制整个 provider。依赖采用发布版本和锁文件，按实际依赖许可证更新第三方说明；本次仅设计，未安装 Rig 或复制源码。

### 10.3 统一错误与业务控制

模型适配器统一返回结构化内容、结束原因、token 用量、延迟与类型化错误。用能力检测确认结构化输出可用；请求失败不得改用未授权来源。来源和模型在每个运行开始时冻结，运行中改设置只影响新运行。

| 故障 | 自动动作 | 用户看到的处理 |
| --- | --- | --- |
| 网络短暂中断 / 可重试 5xx / 429 | 遵循服务端重试时间，有限退避，计入总预算 | 当前等待和已尝试次数 |
| 401 / 403 / 额度不足 / 模型不存在 | 停止，不让内容反思循环处理 | 修改连接、额度或模型后继续 |
| JSON 截断 | 缩小工作单元或受控调整输出预算，最多一次格式重试 | 输出格式问题，保留响应诊断摘要 |
| JSON 类型错误 | schema 检查后一次有针对性的重试 | 不把浮点数 / 空正文当作脚本 |
| 内容问题 | 结构化问题单 → 有界局部修复 | 哪段、为什么改、改了什么 |
| 缺字幕证据 | 保留素材，等待输入 | 补字幕或人工确认，不换模型猜剧情 |
| 配音 / 渲染失败 | 只重试失败媒体单元 | 不要求重新下载或重写全稿 |

字幕、模型输出和远端错误文本均为不可信数据，不能改变系统指令、执行工具或指定任意路径。API Key、Cookies 不进入证据包、提示词、运行日志或设计文档。选择本地导演不代表下载和网络 TTS 也完全离线，界面需分别说明。

## 11. 界面设计

主页面只保留用户能理解的五个工作区：

1. **任务**：运行 / 待修改 / 待确认 / 已成片，支持重试、停止、真删除。
2. **素材**：原视频、原字幕、派生修正对照、缺失或可疑位置、重新获取入口。
3. **导演稿**：段落与因果结构；点问题直接展开原字幕依据、修改建议和前后版本。
4. **样片与声音**：播放样片、选择声线；“事实不对 / 太啰嗦 / 声音不行 / 画面不搭”落到具体段落问题单。
5. **成片**：候选与已发布版本切换、质量检查、确认发布、打开文件。

默认显示简短状态，例如“正在核对第 4 段人物归属”“只重配第 6 段声音”。高级面板才展示模型、token、版本和技术日志。

“重试”表示继续失败工作；“重写这一段”表示局部创作；“重新设计整片”表示新分支。三个按钮不可同义。修复前后可对照，不把自动修复悄悄写回用户手改版本。

## 12. 验收与 A/B：验证模式是否真正改善效果

固定同一字幕、制作要求、模型、声音与工具版本，比较当前样片链路 A 与 V2 有界反思链路 B。先用现有任务，再选至少三种不同材料质量的任务；样本数为试点规模，不用于统计上夸大效果。

- 事实：人工标注的无依据断言、错误人物归属、剧中剧混淆；报告数量与具体位置。
- 叙事：冻结关键事件清单后的覆盖、重复信息、因果断裂、钩子兑现；覆盖率必须人工抽查。
- 音画：人为补冻帧应为零、口播与原声冲突、明显字幕不同步、发音问题。
- 体验：盲看同一开头样片的偏好、愿不愿继续看；不要只让参与生成的模型评自己的稿。
- 效率：总调用 / token / 费用、实测等待、修复次数、人工修改时间、崩溃恢复与缓存命中。

必须包含回归案例：错误登山者归属；361 / 368 字差异；空 MP3；JSON EOF；403 额度耗尽；字幕清洗后不足；实测配音比所选画面长；评审遗漏段落；修复后新增幻觉；预算耗尽；手改与后台修复冲突；删除进行中的任务；重启后不得复活已删除任务。

发布标准分两层：技术自动测试全过；用户对样片事实、叙事、声音和画面作明确确认。没有实片观看就标“技术检查通过，观感待确认”，不宣布商业质量达标。

## 13. 分阶段落地与源码位置

以下模块是拟新增 / 拆分位置，不是已存在能力。

| 顺序 | 实施内容 | 建议源码位置 | 完成条件 |
| --- | --- | --- | --- |
| P0 | Rig 版本与两来源合约验证；统一时长口径、错误分类、V2 schema、运行 / 版本表 | `services/llm.rs`、`models/production.rs`、`models/review.rs`、`services/run_store.rs` | Rig 编译与接口合约、schema 与迁移测试通过，旧任务仍可打开 |
| P1 | 基于 Rig 的创作 / 评审隔离、问题单、局部修改、预算与回退 | `services/reflection.rs`、`services/llm.rs`（薄封装） | 模拟模型测试证明不会无界循环、越界改稿或错误发布 |
| P2 | 将现有样片接入该控制器与统一状态 | `services/sample.rs`、`OpeningSamplePanel.tsx` | 同一素材 A/B 样片可播放、对照、人工验收 |
| P3 | 将整片 MAP / REDUCE 迁入 V2 段落模型 | `services/director.rs`、`services/evidence.rs` | 长片关键因果覆盖与局部恢复通过，样片和整片共享模型 |
| P4 | 实测配音、多轨时间线与渲染验收 | `services/timeline.rs`、`services/media_review.rs`、`services/ffmpeg.rs` | 完整成片不靠定格补时，原声与口播可独立验收 |
| P5 | 发布、恢复、删除、版本对照与偏好记忆 | `commands/pipeline.rs`、`useTaskQueue.ts`、审稿组件 | 中断 / 重试 / 删除端到端测试通过 |

运行可靠性基础应随 P0/P1 建立；P5 是全流程验收，不是等到最后才考虑删除和恢复。按 V2 功能开关逐步放量，不直接删除旧渲染器。旧稿迁移为“待复核候选”，只有用户确认后才启用新流程；回退开关保留 V1 读取和旧成片播放，不覆盖任何既有文件。

优先验证 Rig 与样片反思的实际收益，再扩展全片。首个实现分支见开头进度；没有修改用户模型设置或任务素材，也尚未完成新方案的真实视频生成验收。
