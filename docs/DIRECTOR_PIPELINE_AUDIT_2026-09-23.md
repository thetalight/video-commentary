# AI 导演流程深度审计与 v11 整改

## 审计对象

失败信息：终审旁白约 423.8 秒，发布下限约 688.1 秒（2753 字）。本次审计读取了任务已有的 Story Plan、分章初稿、事实核验稿和整片终审检查点；没有修改字幕原文、`META.json` 或任务素材。

## 失败不是一个“少写了几字”的问题

| 阶段 | 段数 | 旁白字符 | 相对上一阶段 |
| --- | ---: | ---: | ---: |
| 11 章 Writer 初稿合计 | 40 | 2369 | 第一次交付即低于 2753 字下限 |
| 分章事实核验后 | 40 | 1925 | -18.7% |
| 整片合并后的首个终审候选 | 34 | 1615 | -16.1%，并丢失 6 段 |
| 最终接受稿 | 33 | 1695 | 约 423.8 秒 |

旧流程存在三个互相叠加的结构问题：

1. **发布要求只在最后检查。** Writer 收到的是建议，不是可验证的交付合同，因此一开始就欠账；事实核验和终审都可以继续自由缩写。
2. **Writer 同时承担编剧和圈画面。** 模型生成旁白时还要决定时间码与 shots，部分 Narrative Unit 跨越几百秒并包住其他 Unit；分章看似合法，整片合并时发生重叠，只能裁掉段落。
3. **终审角色越权。** 章节已经做事实核验，整片 Reviewer 又连续多轮从自己的新版本继续改写。它把“事实检查”做成了“再次摘要”，每轮都会损失叙事状态、因果和字数。

从剪辑导演角度，问题不在“30% 是否应该放宽”，而在于**旁白预算、故事取舍、文案、证据镜头和终审没有使用同一份制作合同**。只改提示词或在结尾自动补写，都会继续制造注水、声画不足和反复失败。

## v11 的新制作合同

```text
字幕事实
  → Story Beats
  → Story Model（人物、关系、线索）
  → Story Plan（剧情取舍）
  → 单向 Narrative Units
  → Narration Budget（发布下限前置）
  → Chapter Script（AI 只写 unit_id → narration）
  → Timeline Mapper（程序按 beat_id 选证据镜头）
  → 章节事实核验（纠错，不做摘要）
  → 一次整片硬问题检查
  → 声画储备 / TTS / 渲染
```

### 1. 预算前置

程序根据有效字幕覆盖计算发布下限，并在证据上限内为初稿保留事实核验余量。总预算按 Unit 重要度和证据量分配；每个 Unit 的最低交付量写进 JSON Schema，而不只存在于提示词里。检查点 `narration-budget.json` 可直接审计全片下限、Writer 目标、证据上限和每个 Unit 的预算。

这不是“本章差 7 字就重写”的旧式闸门。Writer 一次完成结构化交付；终审不再承担补字任务。

### 2. 文案与剪辑解耦

Writer 输出 `chapter-*.script.json`，只包含每个 Unit 的旁白。它没有权限自选时间码。程序根据 Story Planner 已批准的 `beat_ids` 生成镜头，因此：

- 文案事实与画面证据来自同一 Unit；
- 一个 Unit 对应一个完整叙事段，不会退化成逐句字幕摘要；
- 不再出现 AI 用一个超大时间窗包住中间剧情；
- 时间轴错误不会通过“重写文案”来掩盖。

### 3. Narrative Unit 必须时间单向

如果 Planner 产生 `A → B → A` 的交错引用，程序会在写稿前拆成三个连续 run。Unit 可以跳过不重要的字幕，但不能跨过另一个已选 Unit 后再折返。超过数量上限时，只允许合并时间相邻的 run。

### 4. Reviewer 降权

- 章节 Reviewer 只纠正无依据事实，并被明确要求保留原段已证明的叙事作用和相近信息密度；
- 整片 Reviewer 只运行一轮，只处理人物合同冲突、剧情顺序、称呼、实质重复和 ASR 编号；
- “更简洁”“文风偏好”和泛化心理词不再触发整段重写；
- 如果整轮修改会让旁白低于发布下限，程序拒绝整轮修改，保留章节事实核验后的版本。

### 5. 跨章画面边界

每章最后一段在扩选画面时，提前使用下一章首镜作为硬边界。画面可以向本章安全空档扩展，但不能为了容纳口播抢占下一章证据。

## 仍然会阻断发布的真实问题

v11 不承诺用重复或虚构内容“永远凑够”。以下情况仍应阻断，因为继续渲染只会产出坏片：

- 大量 Story Unit 在事实核验中被证明完全没有字幕证据；
- 字幕本身严重错位、缺失或把片中节目/采访当成主线；
- 选定剧情的原速画面物理容量不足以承载配音，且无法在相邻安全区扩选；
- 本地模型不遵守结构化 Schema 或服务中断。

区别是：正常的字数预算不再拖到最后才失败；真正的问题会在对应层暴露，并留下可追溯检查点。

## 88% 卡死补充修复

首个真实 v11 运行恢复 Story Plan 后停在 87.5%。检查点证明 Ollama 尚未开始写第一章，卡点位于同步预算分配：该片 Planner 只返回 12 个宏观 Unit，其中 10 个普通旁白 Unit 在原 180 字固定上限下无法承载约 3900 字初稿预算；循环判断又把两个固定为短引导的原声 Unit 误认为仍可增长，因此永不收敛。

修复后：

- 预算分配只检查真正可调整的普通旁白 Unit，找不到可调整项立即退出，不存在无限循环；
- 普通 Unit 的容量根据本次总预算动态确定，不再假定所有电影都能用 180 字以内的段落承载；
- 如果本地模型忽略 Story Planner Schema 的 `minItems`，程序会把包含多个节拍的宏观 Unit 按时间顺序拆开，直到达到本片规划下限；不虚构节拍，也不拆单个节拍；
- 预算落盘后进度更新为“Story Plan 已整理为 N 个连续叙事单元，旁白预算已分配”，便于区分同步规划与 Ollama 写作阶段；
- 新增 12 Unit / 2 原声 Unit / 3909 字真实形态回归测试，以及宏观 Plan 自动拆分测试。

## v12：《入殓师》人物串线与“字幕摘要体”整改

在 v11 跑通后，`《入殓师》`真实任务暴露出另一个层级的问题：成稿虽达到发布字数，但仍出现母亲、妻子、同事说话对象串线；“纳棺/农家”“石头/柿子”等 ASR 同音错误被当成确定事实；同一宏观 Unit 拆分后又生成了内容近似的相邻段。这说明“流程能完成”不等于“故事讲对了”。

v12 不引入联网电影资料作为生产依赖，导演仍只依据字幕，但增加以下合同：

1. **Story Model 反证审校。** 初版人物与关系模型生成后，新增一次全片连续性审计。审计必须检查“已死亡或不在场的人是否被误认成后续说话者”、日语省略主语是否被擅自补成亲属身份、说话人聚类编号是否混入人物别名，以及数字、专有词、同音词是否与上下文冲突。审计输出完整修订模型并保存 `story-model.initial.json`、`story-model.audit.json`；审计不可用时留下 warning，不覆盖初版。
2. **不确定身份降权。** 任一事实只要含 uncertainty，程序把 confidence 强制压到不高于 0.65；Writer 与整片 Reviewer 只有在 confidence 不低于 0.8 且 uncertainty 为空时，才允许据此使用姓名、亲属、婚姻或职业身份。ASR 的“说话人87 / speaker_12”等编号会从人物别名中剔除。
3. **拆分后重建写作目标。** 宏观 Unit 被线性化或拆分后，不再复制原章节的 title、entry/turn/exit 和 narration_goal。程序只根据该子 Unit 自己的 beat_ids 重建叙事目标，防止相邻两段重复讲同一次返乡、面试或入行经历。
4. **按素材密度规划段数。** 长片的 Unit 数量同时由片长和有效 Story Beats 决定；不再用少量大段承载整片，也不恢复到一条字幕一个段落。Writer 的安全余量由发布下限的 1.42 倍降为 1.30 倍，减少为满足机械字数而产生的心理描写和空泛评论。
5. **只复用事实层。** 提示版本升级为 `director-v12-continuity-edited-story`。同一字幕、模型和风格可复用 v11 已完成的 `beats.json`，但旧 Story Model、Story Plan、旁白和终审稿全部失效并重建。因此重新生成不会再耗时重做局部字幕事实提取，也不会把旧的人物串线带回新版。

这套机制无法把错误 ASR 自动变成可信的百科事实：当字幕只能证明“有人解释了某个术语”而不能证明术语本身时，系统应改写成不依赖该词的安全叙述，而不是猜成“农家”或联网抄剧情。用户提供的已核实片名资料适合作为人工审校与回归样本，不作为自动导演跳过字幕证据的理由。

## v13：连续场景与人物命名权

v12 的真实重跑仍然失败：虽然最终压缩为30段，旁白仍把上村的自述解释成“大悟母亲抛弃大悟”，把妻子美香的职业争执写成“同事冲突”，并出现“在前行中前行”等注水句。检查点显示，上游 ASR 为同一人物不断分配不同的“说话人编号”，MAP 模型又把这些编号当成角色线索；部分 Story Beat 跨越50–80秒，但持久化证据只保留前8条字幕，导致后续审校无法看到完整对话。

v13 改为以下事实合同：

1. 原字幕文件保持不变，但任何 LLM 输入都会移除不稳定的 ASR 说话人编号。人物只能依据连续台词中的姓名、称呼、问答关系和事件状态识别。
2. MAP 分块增加前90秒和后45秒上下文；上下文只用于理解场景与省略主语，模型只能从 CORE 区间产出节拍。这样分块边界不会把一场争执的前因与说话对象切断。
3. 单个 Story Beat 最长35秒，超长场景必须按可观察变化拆分；每个节拍最多保存32条原字幕证据，不再只保留开头8条。
4. StoryClaim 新增强制 `evidence_quotes`。人物事实和关系事实必须逐字引用所列 beat 中的原字幕；程序无法匹配的引句会删除该事实。含 uncertainty 的事实仍被压到0.65以下，不能获得姓名、亲属、婚姻、职业或说话对象的命名权。
5. Story Planner 和 Writer 只接收 `story-model.trusted.json`，其中仅保留 confidence≥0.8、uncertainty 为空且引句可追溯的人物事实。Story Beat summary 中的猜测不能绕过可信人物表。
6. 人物连续性反证调用失败、长片连3条可信人物事实都无法形成，或章节事实核验调用失败时，流程都会停止；不再以“保留初稿/草稿”方式把未经核验的内容发布为成片。
7. 终审增加确定性检查，拒绝同段重复句和已知无信息套话。
8. 一帆下载器把站点网页标题与影片标题分离：递归读取播放接口中的影片元数据，并过滤“爱壹帆国际版/海量高清视频免费在线观看”等站点模板标题。

提示版本升级为 `director-v13-scene-grounded-speaker-safe`。由于 MAP 输入与证据合同已改变，v12 的 `beats.json` 不再复用；现有字幕仍然复用，但剧情节拍、人物模型、Story Plan 和旁白会完整重建。

## 《入殓师》质量根因归因

对任务 `job-1788396413406-sehcf1` 的 v12 检查点做了定量检查。当前生产字幕不是平台官方字幕，而是 `iic/SenseVoiceSmall` 对原片音轨生成的 `source.sensevoice.srt`；VAD 与说话人模型均为 `zh-cn` 版本。1231 条字幕全部带有聚类说话人前缀，却产生了 362 个不同编号，另有 20 条韩文串音和 74 条去掉编号后仅剩拉丁字母的识别结果。旧 MAP 的 61 个节拍中，39 个把说话人编号写进摘要，11 个超过35秒，33 个包含“可能、暗示、心理、揭示、反映、迫使、内心”等解释性词语。

因此本样本的质量问题不是单一模型导致，建议按以下工程责任估算：

- **ASR 与当前字幕底稿：45%。** 日语长片使用中文向 VAD/说话人模型，导致数字、专名、同音词、多语言和角色切分不可靠。“納棺師”被识别成“能幹師”属于典型上游错误。
- **导演编排与证据治理：35%。** 旧流程把不稳定说话人编号当作人物线索，允许超长节拍只保留局部证据，并让全部 confidence 为0.65、带 uncertainty 的人物推断继续进入规划和写作。它把上游噪声放大成稳定但错误的全片人物关系。
- **LLM 本身：20%。** `qwen3.8:27b-mlx` 能生成通顺中文，但面对破碎日语 ASR 时，省略主语、跨场景指代和人物合并能力不足；同一个模型同时承担提取、写作和审校，还会产生相关性自证。字幕在01:52附近已经连续出现“我把儿子留在带广”“你儿子呢”，旧模型仍改写成“主角母亲抛弃主角”，这是 LLM 推理错误与旧证据合同共同造成，不是 ASR 单独造成。

这里的“字幕问题”和“ASR问题”在当前任务中高度重合，因为导演看到的字幕本身就是 ASR 产物。站点标题被保存成“爱壹帆国际版-海量高清视频免费在线观看”则属于下载元数据提取问题，不属于 ASR 或 LLM。

v13 解决的是“不要把噪声升级为确定事实”，不能把错误听写自动恢复成正确日语。若要继续提升事实准确率，优先级应为：平台/内封/画面字幕优先于 ASR；必须 ASR 时使用日语能力更强的模型并关闭不可靠的跨片说话人命名；最后才是更换导演 LLM。正式比较时应固定同一部电影，分别运行“同 LLM + 高质量日语字幕”“同字幕 + 不同 LLM”“同字幕同模型 + v12/v13”，统计人物串线、无证据事实、专名数字错误和重复空话，不能只比较文风。

## v14：移除 ASR，字幕来源改为确定性三级链路

2026-09-24 起，生产流程不再包含 SenseVoice、Whisper 或任何音轨语音识别兜底。相关服务、配置字段、Tauri 命令、前端设置与“重新识别字幕”入口均已删除。旧任务里的历史识别文件属于用户任务材料，不自动删除，但只作为迁移隔离对象，不会被选作新字幕。

新的字幕来源顺序固定为：

1. 平台独立字幕；
2. 视频容器内的文字字幕轨；
3. 基于 macOS Vision 的本地画面硬字幕 OCR。

每次成功选择来源后，应用写入 `TRANSCRIPT.source.json`，审稿界面直接显示来源。平台字幕单独拉取失败不会立刻终止已有任务，而会继续检查本地原片的内封字幕和画面硬字幕。三种来源都不存在时任务明确失败，不再用音频生成一份表面完整、事实却不可靠的字幕。

这一改动切断了《入殓师》样本中最主要的错误放大链：错误听写 → 伪说话人编号 → 人物关系误判 → 全片错误叙事。它不能保证平台字幕或 OCR 本身绝对正确，所以字幕质量检查、可追溯原文、人物证据合同和人工查看原字幕仍然保留。

字幕文件通常不携带可靠的人物关系，甚至没有说话人字段。因此 v14 同时新增 `dialogue-attribution.json`：在 Story Builder 之前，本地 LLM 必须逐剧情节拍明确“关键台词是谁说、主要说给谁听、依据是什么、是否仍有不确定性”。每条判断都必须逐字匹配该节拍的原字幕；低置信或有冲突的判断会被程序降为“身份未确认”。Story Builder 和人物连续性反证审校都接收这份表，但不得把低置信归属写成确定的人名或亲属关系。这样既不依赖 ASR 说话人聚类，也不会为了让流程通过而硬猜角色。
